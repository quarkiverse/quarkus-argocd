= Quarkus ArgoCD

image::https://img.shields.io/maven-central/v/io.quarkiverse.argocd/quarkus-argocd?logo=apache-maven&style=flat-square[Version, link="https://central.sonatype.com/artifact/io.quarkiverse.argocd/quarkus-argocd-parent", align="left"]

Generate Argo CD Application or Project as part of the Quarkus build or using the Quarkus CLI.

== Features

- Generate the Argo CD Application or AppProject Kubernetes custom resources for the Quarkus application
- Command Line interface to install / uninstall and list Argo CD Application(s)
- Integration with Quarkus Helm
- DevServices able to install Argo CD on kubernetes cluster: kind or k3s

== Requirements

- Project added under a version control system and pushed on a repository (e.g. GitHub, etc.)
- A Kubernetes cluster with Argo CD https://argo-cd.readthedocs.io/en/stable/getting_started/#1-install-argo-cd[installed] and https://argo-cd.readthedocs.io/en/stable/user-guide/application-specification/[supporting] `argoproj.io/v1alpha1`.

=== Breaking changes in the next release (after 0.5.0)

The Argo CD model (`io.quarkiverse.argocd.v1alpha1.*`) is generated with https://github.com/sundrio/sundrio[Sundrio].
The upgrade of Sundrio from `0.103.1` to `0.400.1` (https://github.com/quarkiverse/quarkus-argocd/pull/153[#153]) changed the names of the `end*()` methods of the nested builders: they are no longer prefixed with the name of the parent type.

This only affects code that uses the generated model builders directly (e.g. `ApplicationBuilder`).
The extension configuration (`quarkus.argocd.*`), the CLI and the generated resources are unchanged.

[cols="1,1",options="header"]
|===
| Before (0.5.0 and older) | After

| `endApplicationspecSource()` | `endSource()`
| `endApplicationspecHelm()` | `endHelm()`
| `endSyncpolicyRetry()` | `endRetry()`
| `endSyncpolicyBackoff()` | `endBackoff()`
|===

The other nested builders of the model whose `end*()` method was prefixed follow the same pattern: remove the parent type prefix from the method name.

Example:

[source,java]
----
new ApplicationBuilder()
    .withNewSpec()
        .withNewSource()
            .withNewHelm()
                .withValueFiles("values.yaml")
            .endHelm()        // was: endApplicationspecHelm()
        .endSource()          // was: endApplicationspecSource()
        .withNewSyncPolicy()
            .withNewRetry()
                .withNewBackoff()
                    .withDuration("5s")
                .endBackoff() // was: endSyncpolicyBackoff()
            .endRetry()       // was: endSyncpolicyRetry()
        .endSyncPolicy()
    .endSpec()
    .build();
----

== Building

To build the extension use the following command:

```shell
mvn clean install
```

== Usage

To get the Argo CD custom resources generated, it is needed to add the `quarkus-argocd` extension to a Quarkus project.

=== Add the extension to your project

To add the extension to the project, manually edit the `pom.xml` or `build.gradle` file.

==== Manually editing the `pom.xml` file

```xml
<dependency>
    <groupId>io.quarkiverse.argocd</groupId>
    <artifactId>quarkus-argocd</artifactId>
    <version>0.5.0</version>
</dependency>
```

==== Manually editing the `build.gradle` file

```groovy
dependencies {
    implementation 'io.quarkiverse.argocd:quarkus-argocd:0.5.0'
}
```

After this step the Argo CD yaml files will be generated under the `.argocd` directory within the project root as part of the build.

=== Generated resources

The extension generates, under the `.argocd` directory of the Git repository root, one file per resource:

- `appproject-<project-name>.yaml`: the `AppProject`. It is not generated when `quarkus.argocd.app-project.name` is set to `default`, as this project already exists in Argo CD.
- `application-<application-name>.yaml`: the `Application`.

NOTE: Nothing is generated when the project is not in a Git repository with a remote, as the repository URL is required.

Example of an `Application` generated for a project named `my-app`:

[source,yaml]
----
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
spec:
  destination:
    server: https://kubernetes.default.svc
  project: my-app
  source:
    helm:
      valueFiles:
      - values.yaml
    path: .helm/kubernetes/my-app
    repoURL: https://github.com/<owner>/<repository>.git
    targetRevision: HEAD
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    retry:
      backoff:
        duration: 5s
        factor: 2
        maxDuration: 10m
    syncOptions:
    - CreateNamespace=true
    - RespectIgnoreDifferences=true
    - ApplyOutOfSyncOnly=true
----

The values are computed as follows:

[cols="1,2",options="header"]
|===
| Field | Value

| `metadata.namespace`
| `quarkus.argocd.application.namespace`, or the Argo CD control plane namespace: `argocd`, or `openshift-gitops` when the OpenShift deployment target is enabled

| `spec.project`
| `quarkus.argocd.app-project.name`, or the application name

| `spec.destination`
| `quarkus.argocd.server` and `quarkus.argocd.destination-namespace`

| `spec.source.repoURL`
| The URL of the Git remote of the project

| `spec.source.targetRevision`
| `quarkus.argocd.target-revision` (default: `HEAD`)

| `spec.source.path`
| The Helm chart generated for the application. See <<helm-integration>>
|===

The `AppProject` is created in the Argo CD control plane namespace and allows the same destination and the Git repository of the project as source.
When `quarkus.argocd.application.namespace` is set, this namespace is also added to its `sourceNamespaces`.

[[helm-integration]]
=== Integration with Quarkus Helm

The extension depends on https://docs.quarkiverse.io/quarkus-helm/dev/index.html[Quarkus Helm], which generates a Helm chart for the application from the Kubernetes resources produced by the Quarkus Kubernetes extensions.

The generated `Application` deploys this chart with its `values.yaml` file. Its `spec.source.path` is `.helm/kubernetes/<application-name>`, relative to the Git repository root, so the chart must be available at this location in the repository synced by Argo CD.

=== Using the CLI

The project provides a companion CLI that can be used to generate, install / uninstall and list the Argo CD Applications.
The CLI can be added with the following command:

```shell
quarkus plug add io.quarkiverse.argocd:quarkus-argocd-cli:0.5.0
```

==== Regenerating the files:

To re-trigger the file generation:

```shell
quarkus argocd project generate
```

**Note**: Several parameters can be used to configure the generated CR. Use `quarkus argocd project generate -h` to display the usage.

To install the generated `Application` and `AppProject` (optional) custom resources to the currently connected Kubernetes cluster:

```shell
quarkus argocd project install
```
*Note*: In case of un-committed or un-pushed changes the command will prompt users to decide if they want to proceed with the installation.

The `currently connected Kubernetes cluster` is the one that is configured in the `~/.kube/config` file.
It can be overridden by setting in `application.properties` a different API server URL and token. See the `quarkus-kubernetes-client` extension for more details.

To uninstall:

```shell
quarkus argocd project uninstall
```

==== Listing installed applications

To list all Applications installed

```shell
quarkus argocd project list
```

==== CLI options

The `generate`, `install` and `uninstall` commands accept the following options. Each of them overrides the corresponding configuration property of the extension:

[cols="1,1,2",options="header"]
|===
| Option | Property | Description

| `--server`
| `quarkus.argocd.server`
| The Kubernetes API Server URL

| `--appproject-namespace`
| `quarkus.argocd.app-project.namespace`
| The Argo CD control plane namespace where the `AppProject` is installed

| `--application-namespace`
| `quarkus.argocd.application.namespace`
| The namespace where the `Application` is installed

| `--destination-namespace`
| `quarkus.argocd.destination-namespace`
| The namespace where the resources of the application are deployed

| `-p`, `--project-name`
| `quarkus.argocd.app-project.name`
| The name of the `AppProject`

| `--target-revision`
| `quarkus.argocd.target-revision`
| The revision of the Git repository (branch, tag or commit) that Argo CD syncs
|===

Example:

```shell
quarkus argocd project generate --destination-namespace=my-app --target-revision=develop
```

== Dev Services

In dev and test mode, the extension starts a Kubernetes cluster with https://quarkus.io/guides/kubernetes-dev-services[Kubernetes Dev Services] and installs Argo CD on it.
A container runtime (Docker or Podman) is required.

The Dev Service:

- starts a cluster of type `quarkus.argocd.devservices.cluster-type` (default: `kind`)
- installs the NGINX ingress controller
- installs Argo CD `quarkus.argocd.devservices.version` (default: `v2.13.2`) in the `quarkus.argocd.devservices.control-plane-namespace` namespace (default: `argocd`), without the Dex and notifications components
- creates an ingress for the Argo CD server using the host `quarkus.argocd.devservices.host-name` (default: `argocd.localtest.me`)
- forwards the Argo CD server port to `quarkus.argocd.devservices.host-port` (default: `8443`) on the host, unless `quarkus.argocd.devservices.ingress.port-forward-enabled` is `false`

The Argo CD UI can be accessed with the user `admin`. Its password is printed in the application logs and a link to the dashboard is available in the Dev UI.

To disable the Dev Service:

[source,properties]
----
quarkus.argocd.devservices.enabled=false
----

See the `quarkus.argocd.devservices.*` properties in the configuration reference for all the options.
